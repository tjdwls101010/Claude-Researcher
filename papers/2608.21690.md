# 🖇️컨텍스트를 환경으로 다루기 — 장기 실행 에이전트를 위한 프로그래밍적 컨텍스트 관리

## 🎯 무엇이 문제인가

LLM 에이전트는 레포지토리 수준 소프트웨어 엔지니어링(Jimenez et al., 2024; Yang et al., 2024)이나 열린 웹에서의 deep research(Zheng et al., 2025; Wei et al., 2025)처럼 오래 도는 과제에 점점 더 투입된다. 단일 턴 생성과 달리 이런 과제는 모델 호출, 도구 실행, 관찰, 실패, 수정이 길게 이어지는 trajectory로 전개된다. trajectory가 길어지면 *에이전트 하네스*의 중심 문제는 컨텍스트 관리가 된다. 세션 히스토리는 계속 쌓이는데 모델 호출 하나하나는 유한한 컨텍스트 윈도 위에서 동작하기 때문이다. 게다가 모델이 실제로 신뢰성 있게 활용할 수 있는 컨텍스트는 명목 윈도보다 훨씬 작다. 긴 입력에서의 검색과 추론은 입력 길이에 따라 열화한다(Modarressi et al., 2025; Zeng et al., 2026).

지금까지의 시스템은 이 문제를 대체로 *컨텍스트 압축* 아니면 *외부 메모리*로 다뤘다. 실무에서 지배적인 쪽은 압축이다. 기존 방법들은 오래된 구간을 잘라 내거나, 도구 출력을 버리거나, 이전 trajectory 조각을 요약으로 대체한다(Kang et al., 2025; Ye et al., 2025). Claude Code, Codex CLI, Cursor 같은 프로덕션 에이전트도 컨텍스트 윈도가 한계에 가까워지면 비슷한 compaction 메커니즘을 쓰는 것으로 알려져 있다. 외부 메모리 시스템은 선택된 사실이나 에피소드를 별도 저장소로 추출해 두고 나중에 의미 기반 또는 구조화된 인터페이스로 검색한다(Packer et al., 2023; Wu et al., 2025; cao2026remember). 두 갈래는 같은 방식으로 근본적으로 손실적이다. 에이전트는 히스토리를 요약이나 메모리 저장소를 통해서만 보게 되므로, 그것들이 남기지 못한 세부는 원본 로그가 디스크에 그대로 있어도 손이 닿지 않는다. 그런데 장기 과제는 정확한 과거 증거를 요구하거나 과거 이벤트들 위에서 자명하지 않은 계산을 요구할 수 있다. trajectory에서 멀리 떨어져 생성된 두 도구 출력을 비교하는 일 같은 것이다. 어떤 정보가 필요할지도, 어떤 연산이 필요할지도 미리 알 수 없으므로, 관찰 시점에 만들어진 어떤 요약도 나중에 필요한 것을 보존한다고 보장할 수 없다.

이 논문이 제시하는 *Scroll*은 에이전트의 히스토리를 모델 컨텍스트 바깥에 두고(Zhang et al., 2025) 그것을 실행 가능한 *Session Environment*로 표현한다. append-only Event Log가 안정적 주소와 provenance와 함께 상호작용 trajectory를 보존하고, 샌드박스된 영속 Python kernel이 모델 호출을 넘어 살아남으면서 resident 변수들의 타입 있는 namespace를 유지한다. 따라서 이 상태 중 무엇이든 Python 객체로 materialize되어, 프롬프트로 직렬화되지 않은 채 여러 추론 스텝에 걸쳐 재사용될 수 있다.

이 설계는 컨텍스트 관리를 *프로그램 작성*으로 바꾼다. 현재 모델들이 이미 매우 잘하는 일이다. 모델은 `exec` 액션을 발행해 Event Log를 검색하고 확장하며, 허용된 리소스에 접근하고, 도구를 호출하고(Anthropic, 2025b), resident 변수 위에서 계산한다. 검색된 레코드, 도구 출력, 중간 계산은 `print`로 명시적으로 내보내지 않는 한 kernel에 남고, 하네스는 print된 것만 다음 모델 컨텍스트에 관찰로 삽입한다. 즉 `exec`가 환경에 어떻게 접근하고 그것을 어떻게 변환할지를 결정하고, `print`가 Session Environment 위의 어떤 projection이 모델의 *working view*로 들어올지를 결정한다.

working view가 예산에 가까워지면 하네스는 오래된 구간을 evict한다. compaction과 달리 eviction은 view만 바꿀 뿐 밑에 깔린 기록은 건드리지 않는다. evict된 이벤트는 안정적 주소 아래 Event Log에 그대로 남아 있고, 모델의 프로그램이 필요할 때 그것을 찾아 materialize한다. Scroll은 여기에 더해 *eviction index*를 view 안에 유지한다. view를 떠난 것이 무엇인지에 대한 간결한 지도다. 검색은 에이전트가 물어볼 생각을 한 것만 되찾아 주는 데 반해, 이 인덱스는 더 이상 보이지 않는 히스토리의 존재 자체를 에이전트에게 계속 알려 준다. 각 항목은 evict된 이벤트들의 정확한 주소를 앵커로 갖고 있어서 원본을 필요할 때 materialize할 수 있다.

백본을 Qwen3.8-Max로 두었을 때 Scroll은 LongMemEval_(*S*)에서 **94.8%**, BEAM_(*10M*)에서 **73.1%**로 최고 공개 메모리 시스템을 5.1점 앞서고, LOCA_(*256K*)에서 **86.7%**로 최고 공개 장기 에이전트를 37.4점 앞선다.

기여는 세 가지다. 첫째, 장기 컨텍스트 관리를 매 스텝마다 영속적 Session Environment 위의 working view를 고르는 문제로 형식화한다. 기존 접근은 이 선택을 미래의 필요가 알려지기 전에 고정하지만, Scroll은 그것을 모델이 쓰는 프로그램으로서 질의 시점까지 미룬다. 둘째, append-only Event Log, durable storage, 샌드박스된 영속 Python kernel을 결합한 실행 가능한 컨텍스트 기반을 구현한다. 모델은 `exec`를 통해 환경을 다루고, 그 안에서 명시적 `print` 출력만이 모델이 볼 수 있는 컨텍스트로 넘어온다. 셋째, 히스토리를 잃지 않으면서 working view를 예산 안에 유지하는 알고리즘을 제시한다. evict된 구간은 Event Log에 온전히 남고, 주소를 앵커로 갖는 간결한 항목으로 색인되어 에이전트가 곧장 찾아갈 수 있다.

## 🧩 문제의 형식화: 세션 상태와 working view

에이전트 세션은 사용자 메시지, 모델 응답, 도구 호출, 도구 결과 같은 *이벤트*의 열 $e_{1},e_{2},\ldots$를 만들어 내고, 각 이벤트는 *payload*(원본 내용, 예컨대 전체 도구 출력)를 갖는다. $t$ 스텝 이후의 세션 상태는 다음과 같이 쓴다.

$$S_{t}=(L_{t},\;P_{t},\;V_{t}),$$ (1)

여기서 $L_{t}$는 이벤트별 메타데이터가 붙은 이벤트 열, $P_{t}$는 $L_{t}$가 참조하는 payload들, $V_{t}$는 파생된 보조 상태다(Scroll에서는 변수 namespace, 다른 시스템에서는 메모리 저장소나 요약 버퍼). 그런데 각 모델 호출은 $|c_{t}|\leq C$ 토큰의 *working view* $c_{t}$만 소비한다. $C$는 모델의 명목 컨텍스트 윈도다. *컨텍스트 관리 문제*는 매 스텝 다음 view, 즉 사상 $S_{t}\mapsto c_{t+1}$을 고르는 일이다.

핵심은 그 선택이 *언제* 이뤄지느냐다. 기존 접근은 사상 $S_{t}\mapsto c_{t+1}$을 미래의 필요가 알려지기 전에 고정한다. 압축은 trajectory가 자라는 동안 손실 연산자 $\phi$를 적용해 $c_{t+1}=\phi(c_{t},\,e_{t})$로 각 구간이 compaction될 때 어떤 정보가 살아남을지를 결정한다. 외부 메모리는 ingestion 시점에 추출 연산자 $\psi$를 적용해 $V_{t}=\psi(V_{t-1},e_{t})$로 무엇이 저장되고 나중에 어떻게 검색될 수 있는지를 고정한다. 어느 쪽이든 축약된 표현이 그것이 요약한 히스토리를 대체하므로, 빠뜨린 것은 복구 불가능하다.

Scroll은 선택을 질의 시점으로 미룬다. 전체 상태 $S_{t}$는 컨텍스트 바깥에 손실 없이 남아 있고, 사상 $S_{t}\mapsto c_{t+1}$은 모델이 스텝 $t$에 작성하는 *프로그램* $\pi_{t}$다. 프로그램은 $S_{t}$ 위에서 실행되고, $V_{t}$를 갱신하고, 다음 호출을 위한 유한한 관찰을 내보낸다. 무엇을 recall하고 계산하고 노출할지는 모델이 정하고, 하네스는 durable storage, 안정적 주소 지정, 샌드박스 실행으로 그 결정들을 안전하게 만든다. 정책이 코드로 표현되므로 프로그램의 일반성을 그대로 물려받고, 하네스를 바꾸지 않아도 백본의 코딩 능력과 함께 좋아진다.

## 🗄️ Session Environment: 세 부분

![](sources/images/2608.21690v1/scroll_system_image.png)

*Figure 1: Overview of Scroll. Scroll keeps the full session in a persistent, executable Session Environment; model-written code retrieves and computes over it via exec, and print selects the working view exposed to the next model call.*

Figure 1은 왼쪽에 기존 방식, 오른쪽에 Scroll을 놓고 대비한다. 왼쪽 "Traditional context management"는 프롬프트 안의 직렬화된 텍스트를 관리한다. Historical sessions(`[s-12] prefers economy`, `[s-31] avoid toll roads`)는 extract를 거쳐 memory store로 가고, 현재 세션(U: "Plan my Tokyo trip." → A: `search_flights` → 수백 개 요금 → A: `search_routes` → 공항 드라이브 옵션 → U: "Book a flight I'd like and plan my drive.")은 truncate/summarize를 거쳐 model context로 들어가며, model context에는 retrieved memory와 session summary만 남는다. 오른쪽 "Scroll: context management as code"에서는 모델이 코드를 써서 자기 working view를 구성한다. ① 모델이 `exec`로 모델 작성 코드를 Session Environment(영속적, 프롬프트 바깥)에 보내고, 그 안의 Event Log(append-only)는 `seq 0087 U prefers economy`, `seq 0912 U avoid toll roads`(이전 세션), `seq 1103 A search_flights`, `seq 1893 U book one I'd like`(현재 세션)를 담는다. ② 큰 payload는 Durable storage로 persist된다(`flights.json`, `routes.json`이 payload storage에, History.db가 SQLite·FTS5로). ③ retrieve·compute 화살표가 Python kernel(namespace persists)로 이어져 `preference: dict ← s-12, s-31`, `flights: DataFrame ← seq 1103`, `routes: DataFrame ← seq 1487`이 resident 변수로 남는다. ④ `print`가 model context(working view)로 넘어가 현재 관찰을 만든다. 이전 세션 쪽에는 `economy fare ✓`, `no-toll route ✓`가, 현재 세션 쪽에는 `Flight results ✓`, `Route results ✓`가 놓인다. ⑤ 그것이 다음 모델 호출로 돌아간다. 오른쪽 아래에는 evict 시의 Eviction Index가 있다. Tier 2는 `seq 1000-1400 [flights]`처럼 거칠고, Tier 1은 `seq 1487 [routes: done · next: book · routes.json]`처럼 세밀하며, 위로 갈수록 오래되고 거칠다. 복구는 `ms.expand(seq_lo, seq_hi)`로 한다. 도구 호출과 그 결과는 kernel에 bind된다.

**append-only Event Log ($L_{t}$).** Event Log는 에이전트 세션들의 durable한 ground-truth 기록이다. 세션 경계를 가로지르는 단일 append-only 로그이며, 모든 상호작용은 미래 질의가 필요로 할 메타데이터(role, 세션 및 에이전트 식별자, 타임스탬프, 도구 상태)를 실은 타입 있는 이벤트로 append되고 변경 불가능하며 단조 증가하는 `seq`를 받는다. 구현은 이벤트를 SQLite에 저장한다. 검색은 embedding이 아니라 BM25를 기본으로 삼는다. 결정적이고 index 시점에 모델 호출이 필요 없기 때문이다.

**durable storage ($P_{t}$).** payload는 상호작용이 만들어 낸 원본 내용이다. 전체 도구 결과나 생성된 artifact 같은 것이다. 로그는 상호작용이 일어났다는 사실을 기록하지만 그 모든 바이트를 이벤트 행에 담을 필요는 없다. 작은 payload는 SQLite 안에 인라인으로 남고, 큰 것은 파일시스템의 JSON 또는 artifact storage로 옮겨지며, 행에는 유한한 미리보기와 복구 포인터만 남는다. 외부화된 payload는 lazy handle(`ToolResultRef`, `ArtifactRef`)로 접근한다.

**영속 런타임과 resident namespace ($V_{t}$).** 샌드박스된 Python kernel이 세션 내내 모델 호출을 넘어 지속되고, 그 namespace는 *환경 객체*를 담는다. resident Python 값과 lazy handle이며, 각각은 자신이 어느 이벤트에서 유래했는지 밝히는 타입·크기·provenance 메타데이터를 갖는다. 프로그래밍적 도구 인터페이스(Anthropic, 2025b)를 통해 발행된 도구 호출은 Python 객체를 돌려주므로 나중의 프로그램이 그 위에서 연산할 수 있다. 하네스는 모든 호출 앞에 *namespace digest*를 붙인다. resident 변수 각각의 이름, 타입, shape를 짧게 나열하고 작은 스칼라 값은 인라인으로 보여 주는 목록이다. 모델이 작성한 코드는 fail-closed 샌드박스에서 실행된다. Event Log는 kernel에서 읽기 전용이고, 데이터베이스·파일시스템·네트워크·도구 접근은 하네스가 명시적으로 선언한 capability로 제한된다.

## ⌨️ exec는 어떻게 접근할지, print는 무엇을 노출할지

Scroll은 과제 실행과 컨텍스트 구성 양쪽에 CodeAct 스타일 인터페이스(Wang et al., 2024)를 쓴다. 통제된 capability 객체 `ms`가 durable history 위의 모델 대면 *memory surface*를 이루며, 물리적 백엔드를 네 연산 뒤로 추상화한다.

*Table 1: The model-facing interface factorizes context construction into location, materialization, computation, and exposure.*

| **Operation** | **Interface** | **Role** |
|----|----|----|
| Locate | `ms.search(query, k, ...)` | Find candidate Event Log records via BM25-ranked full-text search and structured scope, kind, and time filters; each hit carries its stable `seq` address. |
| Materialize | `ms.expand(seq)` `ms.expand(seq_lo, seq_hi)` | Recover exact turns or sequence spans, and load externalized payload contents behind lazy handles. |
| Compute | Ordinary Python and permitted database, filesystem, and tool interfaces | Filter, join, aggregate, resolve updates, inspect artifacts, or construct derived state. |
| Expose | `print(value)` | Return the selected projection as a bounded observation; everything else stays in the kernel. |

Figure 2는 Figure 1의 여행 계획 과제를 세 개의 `exec` 셀로 따라간다. 맨 위 Model context(working view)는 고정 prefix(system prompt + tool defs) 위에 셀마다 들어오는 것을 표시한다. 셀 1에서는 3 rows, 셀 2에서는 20 previews, 셀 3에서는 2 events + 2 rows다. 셀 1(`exec`, call tools)은 `flights = search_flights()`, `routes = search_routes()`, `print(flights.head(3))`을 실행한다. 둘 다 kernel에 bind되고 3행만 print된다. 셀 2(`exec`, locate history)는 `previews = ms.search("prefer OR avoid", k=20)`과 `print(previews)`를 실행한다. previews와 `seq`가 working view로 들어오며 economy 선호와 무톨게이트 선호가 드러난다. 셀 3(`exec`, materialize·compose)은 `prefs = ms.expand(87, 912)`, `fl = flights[flights.cabin=="economy"]`, `rt = routes[routes.tolls==0]`, `print(prefs, fl.nsmallest(1,"price"), rt.nsmallest(1,"mins"))`를 실행한다. DataFrame은 resident로 남고 검증된 선호와 가장 싼 항공편·가장 빠른 무톨 경로만 working view로 들어온다. 아래쪽 Python kernel(resident namespace)에는 턴을 가로질러 `flights`, `routes`, `previews`, `prefs`, `fl`, `rt`가 남는다. 맨 아래 Event Log(append-only, ground truth)에는 `seq 0087 prefer economy`, `seq 0912 avoid tolls`, `seq 1103 search_flights ▸ 142 rows`, `seq 1487 search_routes ▸ 38 rows`가 있고, 셀 1은 호출과 전체 결과를 append하며, 셀 2는 `ms.search`로, 셀 3은 `ms.expand(87, 912)`로 로그를 읽는다.

즉 셀 1은 전체 도구 결과를 kernel의 resident 변수 `flights`와 `routes`에 bind하고 몇 행만 print한다. 셀 2는 진술된 선호를 Event Log에서 검색하고, 매칭된 미리보기와 `seq` 주소가 working view로 들어와 사용자가 economy 객실과 무톨 경로를 선호한다는 사실을 드러낸다. 셀 3은 그 두 이벤트를 expand해 원문 그대로의 기록을 얻고, resident 변수들을 그에 맞춰 필터링·랭킹한 뒤 두 선호 턴과 가장 싼 economy 항공편, 가장 빠른 무톨 경로를 함께 print한다. 대량의 도구 결과는 working view에 결코 들어오지 않으며, 모든 호출은 전체 결과와 함께 Event Log에 append되어 `seq`로 주소 지정된다.

## ♻️ 예산은 지키되 되돌릴 수 있는 eviction

세션이 자라도 working view는 유한하게 유지돼야 한다. Scroll은 working view가 예산 $\rho C$를 넘을 때마다 발동하는 eviction 절차(Algorithm 1)로 이를 유지한다. 절차는 먼저 live 턴을 Event Log에 영속화하고, 활성 턴·최근 tail·가장 새 도구 결과를 보호한다. 나머지는 복구 비용이 낮은 순으로 evict된다. 완료된 도구 payload가 먼저 접히는데, `seq` 포인터 하나만으로 복구되기 때문이다. 구간 전체를 제거하는 것은 그러고도 view가 예산을 넘을 때뿐이다. view를 떠난 것은 잃어버린 것이 아니다. Event Log에 원문 그대로 남고, 이 절차의 유일한 불변식은 제거하는 모든 것이 주소로 접근 가능한 채 남는다는 것이다.

*Algorithm 1 Recoverable context eviction*

    1: working view $c$, Event Log $\mathcal{L}$, eviction index $\mathcal{I}$, budget $\rho C$, tier width $k$
    2: bounded $c$ and updated $\mathcal{I}$; removed spans stay recoverable from $\mathcal{L}$
    3: if $|c|>\rho C$ then
    4:   $\mathcal{L}\leftarrow\textsc{Persist}(c,\mathcal{L})$ $\triangleright$ live turns become durable
    5:   $R\leftarrow\textsc{Protected}(c)$ $\triangleright$ active turn, recent tail, newest tool results
    6:   $c\leftarrow R\,\cup\,\textsc{FoldPayloads}(c\setminus R)$ $\triangleright$ payloads $\to$ seq pointers
    7:   $E\leftarrow\textsc{SelectSpan}(c\setminus R,\;|c|-\rho C)$ $\triangleright$ oldest completed span above budget
    8:   $c,\ \mathcal{I}\leftarrow\textsc{EvictToIndex}(c,\;E,\;\mathcal{H}[E])$ $\triangleright$ $E$ leaves the view; its headlines enter $\mathcal{I}$, shown in place
    9:   $\mathcal{I}\leftarrow\textsc{RollUp}(\mathcal{I},\,k)$
    10: end if
    11: return $(c,\mathcal{I})$

**headline은 항해의 앵커다.** 어휘 검색은 에이전트가 그 표현을 기억해 낼 때만 evict된 구간을 되찾아 준다. 그래서 Scroll은 위치 기반 항해를 위한 *landmark*도 함께 유지한다. 모델은 응답의 일부로 짧은 *headline*(과제, 검증된 상태, 다음 행동, 상태 표시)을 쓰고, Scroll은 이를 append 시점에 Event Log가 부여한 `seq`에 묶어 주소에서 headline으로 가는 사상 $\mathcal{H}$를 만든다. 어떤 구간이 evict되면 그 headline들이 계층화된 인덱스로 들어간다(Figure 1). 평평한 인덱스는 세션에 선형으로 자라므로 Scroll은 그것을 roll up한다. 각 tier는 최대 $k$개의 블록을 갖고, 한 tier가 차면 가장 새 블록은 전체 세부를 유지한 채 남고 나머지 $k-1$개는 한 줄씩으로 접혀 다음 tier로 병합된다. $n$번의 eviction 후 인덱스는 $O(k\log_{k}n)$개의 블록을 차지하며, 최근 히스토리에는 세밀한 앵커를, 먼 히스토리에는 거친 범위를 제공하고 각각이 `seq` 구간으로 뒷받침된다.

## 🧪 어떻게 검증했나

두 가지 장기 설정에서 평가한다. (1) live 컨텍스트를 넘는 상호작용 히스토리를 검색하고 그 위에서 추론하는 것, (2) 상태가 시간에 따라 자라는 에이전트 환경에서 추론하고 행동하는 것.

**장기 메모리 검색과 추론.** `LongMemEval`(Wu et al., 2025)은 이전 사용자–어시스턴트 대화 히스토리에 대한 질문을 던진다. 답하려면 세션들에 흩어진 증거를 찾고, 시간 의존성과 지식 갱신을 해소하고, 검색된 증거 위에서 추론해야 할 수 있다. 벤치마크는 방해 히스토리 양이 늘어나는 세 가지 설정을 제공한다. `Oracle`은 히스토리에 증거 세션만 담고, `S`와 `M`은 각 질문에 대략 50개와 500개 세션(${\sim}115$K와 ${\sim}1.5$M 토큰)의 히스토리를 짝지어 준다.

`BEAM`(Tavakoli et al., 2025)은 이 평가를 훨씬 더 긴 일관된 히스토리로 확장한다. 질문은 인접하지 않은 증거를 모으거나, 시간에 따른 변화를 추적하거나, 반복된 정보를 중복 제거하거나, 히스토리 전반에 흩어진 사실을 집계하도록 요구할 수 있다. 벤치마크는 네 가지 히스토리 규모(128K, 500K, 1M, 10M 토큰)에 걸치며, 가장 큰 규모인 BEAM_(*10M*)에서는 히스토리를 현재 모델 컨텍스트 윈도 안에서 직접 소비할 수 없다.

**긴 컨텍스트에서의 추론과 행동.** `LOCA`(Zeng et al., 2026)는 가용 환경 상태가 누적되는 동안 추론하고, 도구를 호출하고, 환경을 수정해야 하는 에이전트를 평가한다. LOCA는 도구 사용 trajectory가 자라는 내내 에이전트가 계속 추론하고 행동할 수 있는지를 측정한다. 벤치마크는 *환경 서술 길이*(도구 출력을 통해 보이는 전체 환경 상태의 토큰 수)를 8K에서 256K까지 일곱 구간으로 조절하며, 여기서는 가장 큰 두 구간(128K와 256K)에서 평가한다.

**에이전트 구성.** 주 실험의 백본은 Qwen3.8-Max다. 모든 컨텍스트 관리 방법은 도구 호출과 실행 인프라를 제공하는 에이전트 운영체제 QwenPaw(Agentscope Team, 2026) 위에 구현·평가됐고, 벤치마크가 제공하는 환경에서 Harbor(Harbor Framework Team, 2026)로 오케스트레이션됐다. 보고된 모든 결과를 재현하는 구현은 <https://github.com/niceIrene/QwenPaw/tree/scroll-research>에 있다.

Scroll은 자기 기능을 도구 집합으로 에이전트에 노출하며, 그중 다음 둘이 `exec` 액션을 구현한다. `repl_exec`는 모델이 생성한 Python 셀을 영속 kernel에서 실행한다. 환경 도구들은 하부 서비스로 전달되는 Python 함수로 노출되어 프로그래밍적 도구 호출을 가능하게 하고, 모든 중간 계산은 kernel에 머물며 명시적이고 예산이 걸린 `print` 출력만 모델의 working window로 들어온다. `recall_history_python`은 memory surface `ms`가 미리 bind된 셀을 실행한다. `ms.search`가 evict된 레코드를 찾고 `ms.expand`가 그것을 Python 객체로 materialize하면, 모델은 kernel 안에서 필터링·결합·집계한 뒤 정제된 결과만 print한다.

모든 벤치마크에 걸쳐 단일 system prompt와 한 벌의 컨텍스트 관리 규칙을 쓰며, few-shot 예시는 없다. 각 메모리 벤치마크는 데이터 레이아웃, memory surface 사용법, 증거 선택 관례, 답변 형식을 명시하는 짧은 rubric 하나씩만 기여한다. LOCA에서는 벤치마크의 공식 과제 지시를 수정 없이 쓰고 환경 메타데이터(가용 API와 workspace 경로)만 덧붙인다.

백본에 걸친 일반성을 시험하기 위해 Qwen3.7-Max, Deepseek-v4-pro, GLM-5.2, Kimi-K2.7, 그리고 활성 파라미터 규모가 작은 open-weight 모델인 Qwen3.6-35B-A3B도 추가로 평가하며, 바꾸는 것은 foundation model뿐이다.

**평가 프로토콜.** 두 메모리 벤치마크에서는 각 대화 히스토리를 시간 순으로 세션 단위로 Scroll 세션에 ingest한다. 각 세션 경계에서 raw 컨텍스트는 비워지고, Scroll의 내부 상태(eviction index와 Event Log)만 다음 세션으로 넘어간다. LOCA에서는 각 과제가 벤치마크가 제공하는 초기 환경 상태에서 시작한다. 에이전트는 환경을 직접 탐색하고 행동하며, Scroll이 trajectory가 자라는 동안 컨텍스트를 관리한다.

LongMemEval과 BEAM은 벤치마크가 제공하는 LLM-as-a-judge 프롬프트로 채점하며, judge는 temperature $0$의 Qwen3.6-flash다. LongMemEval은 정확도를, BEAM은 judge 점수를 보고한다. LOCA는 최종 환경 상태를 확인하는 자체 규칙 기반 verifier로 채점하고 정확도를 보고한다. 별도 언급이 없으면 각 과제는 벤치마크가 제공하는 컨테이너에서 랜덤 시드로 한 번 평가되며, 과제마다 모델 대면 입력·출력 토큰과 상호작용 턴 수도 기록한다.

## 🔁 백본을 바꿔도 되는가

Scroll은 컨텍스트를 관리할 환경을 제공하지만 그 사용법을 지시하지는 않는다. 어떤 상태를 어디에 둘지, 어떤 코드를 쓸지는 모델에 맡겨진다. 그래서 Scroll을 효과적으로 쓰는 능력이 한 백본에 특유한 것인지 여러 능력대의 모델이 공유하는 것인지가 자연스러운 질문이 된다. 하네스, 도구, 프롬프트, 컨텍스트 관리 규칙을 고정한 채 두 설정을 여섯 백본에서 다시 돌렸다.

모든 백본이 Scroll을 쓸 수 있지만 강한 모델일수록 더 이득을 본다. 모델이 짧은 프로그램으로 히스토리 데이터베이스를 질의하는 LongMemEval_(*S*)에서는 모든 백본이 비슷하게 이득을 보며, 35B 모델조차 $88.8$에 도달해 최고치($94.8$)와 6점 이내다. BEAM_(*10M*)에서는 격차가 $15$점 이내에 머문다. 그러나 LOCA에서는 과제가 더 긴 trajectory와 더 복잡한 프로그램 합성을 요구하므로 256K에서 격차가 $64$점까지 벌어진다($86.7$ 대 $22.7$). 실패는 프로토콜 수준의 문제가 아니다. 모든 백본이 CodeAct 인터페이스를 지키지만, 약한 모델은 실행 오류를 더 많이 내거나 집계가 많은 과제에서 조기에 종료한다. 따라서 그런 과제에서 Scroll의 천장은 다단계 질의 계획 능력과 증거가 충분한지 판단하는 능력과 함께 올라가며, 이는 frontier 모델 trace 위의 post-training 여지를 시사한다.

원본 레코드를 버리는 것이 가장 치명적인 ablation이다. 손실 변형은 전체 19.9로 떨어지고, 정보 추출·시간 추론·지식 갱신처럼 답이 히스토리의 정확한 값을 보존해야 하는 곳에서는 거의 0점이다. Scroll w/o REPL은 전체 Scroll보다 7.3점 낮다. 직렬화된 도구 결과는 kernel에서 필터링·결합·집계될 수 없기 때문이며, 차이는 여러 레코드에서 증거를 조합해야 하는 능력에 몰려 있다. 지식 갱신(92.5 대 82.5)과 지시 준수(97.5 대 76.3)가 그렇고, 단일 조회 능력은 영향받지 않는다. eviction index 제거는 전체 1.8점을 앗아 가지만, 그 효과는 증거가 히스토리 전반에 흩어져 있어 그러지 않으면 키워드 검색으로 모아야 하는 곳에 집중된다. 선호 준수(89.1 대 74.9), 요약(70.5 대 62.6), 이벤트 순서(64.1 대 58.1)다.

## 🧭 선행 연구와의 위치

**컨텍스트 압축과 외부 메모리.** 대부분의 컨텍스트 관리 시스템은 활성 trajectory를 압축하거나 선택된 정보를 외부에 저장한다. 압축 방법은 이전 상호작용을 요약하거나, 비우거나, 더 짧은 표현으로 접는다(Kang et al., 2025; Ye et al., 2025; Zhou et al., 2026; Kontonis et al., 2026). 외부 메모리 시스템은 대신 사실, 에피소드, 노트를 별도 저장소로 추출해 두고 관련될 때 검색한다(Packer et al., 2023; Tan et al., 2026; Letta, 2026). 두 접근 모두 미래의 필요가 알려지기 전에 어떤 정보가 어떤 형태로 살아남고 어떤 인터페이스로 나중에 닿을 수 있는지를 결정함으로써 모델이 보는 히스토리를 줄인다. Scroll은 대신 원본 상호작용 이벤트와 참조된 payload를 보존하며, 요약과 인덱스는 유한한 working view를 제공하되 과거 증거의 유일한 표현이 되지는 않는다.

**에이전트–환경 인터페이스로서의 코드.** CodeAct는 실행 가능한 Python을 LLM 에이전트의 일반적 액션 인터페이스로 도입했고(Wang et al., 2024), 프로그래밍적 도구 호출과 코드 실행 시스템은 도구 결과가 샌드박스 변수에 남아 선택된 projection을 통해서만 컨텍스트로 들어오게 한다(Anthropic, 2025b; Anthropic, 2025a). 관련 연구는 외부화된 긴 입력 프롬프트에 대한 프로그래밍적 접근(Zhang et al., 2025)과 구조화된 작업 상태(Li, 2026; VISTA, 2026)도 탐구했다. Scroll은 이 원리를 에이전트 세션의 계속 변하는 상태에 적용한다. 그 영속 Python kernel은 모델 호출을 넘어 타입 있는 변수를 유지하며, `exec`가 세션 상태를 검색·변환하고 명시적 `print` 출력만이 관찰 경계를 넘는다.

**손실 없는 세션 히스토리와 항해.** 선행 시스템은 원문 recall 저장소, event-sourced 상호작용 로그, 손실 없는 포인터, provenance로 연결된 메모리를 탐구했다(Packer et al., 2023; Nakajima, 2026; Ehrlich and Blackman, 2026; Zhang et al., 2026). Scroll은 질의 가능한 append-only Event Log를 외부 payload 참조 및 실행 가능한 resident namespace와 결합한다. 세션 내 eviction index는 이렇게 보존된 상태 위의 항해 레이어다. 최근 히스토리는 세밀하고 sequence 주소가 붙은 headline으로, 오래된 히스토리는 더 거친 범위로 표현된다. 관련 영역이 일단 지목되면 원본 이벤트와 payload는 프로그래밍적으로 복구된다. CoALA(Sumers et al., 2024)와 컨텍스트 엔지니어링 서베이(Mei et al., 2025)의 용어로 말하면, Scroll은 실행 가능한 working state와 원문 그대로의 episodic history를 영속적 Session Environment로 잇는다.

Scroll은 질의마다 raw 이벤트에서 그것을 재구성해야 하고, 그곳의 잔여 실패는 검색이 아니라 질의 형성의 오류다.

## 📝 벤치마크가 기여하는 rubric 전문

§3.2의 공용 system prompt와 컨텍스트 관리 규칙 외에, 각 메모리 벤치마크는 rubric 하나씩을 기여한다. LOCA에서는 벤치마크의 공식 과제 지시를 수정 없이 쓰고 환경 메타데이터(가용 API와 workspace 경로)만 덧붙인다.

**BEAM rubric**

```
The user's benchmark conversation history is stored in your durable history as rows with kind='beam_chat_turn'. Rows are chronologically ordered by seq; each session has a distinct session_id; rows carry an ISO created_at.

Recall it with the recall_history_python tool: pass a Python cell that uses the pre-bound ms surface. Search with concise keyword or synonym queries, e.g. ms.search(QUERY, all_agents=True, kind='beam_chat_turn', k=10). Uppercase OR passes through as a boolean operator; otherwise terms are AND-combined. Start with k=5 or k=10 and increase it only when the evidence is insufficient. If a question combines multiple named systems, efforts, or entities, search each one separately instead of putting every name into one AND query. Extract one directly relevant value for each part, preserve its unit, and only then calculate. Each hit already includes the full turn text together with its seq, session_id, role, and metadata; do not call ms.expand merely to pair a user message with its assistant reply. If you must reread a returned turn, call ms.expand only with that hit's exact seq neighbours (lo, hi). For a question about one source date or an inclusive date range, filter on the created_at column (ISO-8601 text, lexically sortable) with ms.sql_query, e.g. "SELECT seq, session_id, role, created_at, content FROM hist.conversation_history WHERE kind='beam_chat_turn' AND substr(created_at,1,10) BETWEEN '2024-07-01' AND '2024-07-31' ORDER BY seq LIMIT 50". For elapsed calendar days between two dates, use ms.days_between(d1, d2).

Treat role='user' rows as evidence of the user's facts, actions, and preferences; an assistant suggestion is not evidence that the user adopted it. Preserve exact numbers, units, and version labels from the most directly relevant user evidence; do not replace them with illustrative values. Do not add repeated historical mentions as separate quantities unless the question explicitly asks for that. When a fact changed, use the latest user evidence only after confirming that the rows describe the same project and the same fact, not merely similarly named work. Base your answer only on recalled conversation evidence. Do not use information from other history kinds. Follow any output-count or formatting constraint in the question exactly. If the requested fact is absent, say so clearly.

Grounding rule (strict): every concrete claim --- each fact, number, name, date, quantity, or event --- must come verbatim in meaning from a turn you retrieved. Never invent specifics to make an answer sound complete.

Decide between answering and saying "not enough information" by what you actually retrieved, not by how hard you searched: if a turn directly states the asked-for fact, give it; if none does, say there is not enough information in the conversation. ## 🔍 실제 trajectory 네 편
```

각 trajectory는 로그의 JSON 형식(`task_id`, `metrics`, `steps`) 그대로 보이되 다음과 같이 축약됐다. 모델이 작성한 코드는 각 스텝의 `"source"` 필드에서 참조된 코드 블록으로 옮겨졌고 모델 자신의 주석을 포함해 그 외에는 편집되지 않았다. `"reasoning"`(행동 전 모델의 사고)과 `"observation"` 문자열은 발췌이며 생략은 `[...]`로 표시된다. 문자열 안의 개행은 문자 그대로 렌더링되고 비ASCII 구두점은 정규화됐다. 회색 `//` 줄은 논문 저자들의 주석이고 로그의 일부가 아니다. trajectory 분석이 결과를 좌우했다고 판단한 스텝은 굵은 색으로 표시된다(`// >>`는 성공을 이끈 스텝, 또는 실패가 결정된 스텝). `seq`는 이벤트의 변경 불가능한 Event Log 주소이고, `[Session n | date]` 접두는 저장된 이벤트의 일부다. judge 점수는 벤치마크가 제공하는 LLM judge의 것이다.

## ⚠️ 저자들이 인정한 한계

Table 2와 Table 6, Table 7의 비교는 통제된 비교가 아니다. baseline마다 reader 모델이 다르고 점수에 실질적 영향을 줄 수 있으며(EmergenceMem은 GPT-4o, Zep은 GPT-5.4, Mastra OM은 GPT-5 mini, Mem0는 GPT-5, Hindsight는 Gemini 3 Pro, Exabase M-1은 Gemini 3 Flash, RAG와 LIGHT는 Llama-4-Maverick, Honcho는 다중 모델 파이프라인, Cognee는 reader를 보고하지 않는다), 각 시스템은 자기가 선호하는 구성 아래의 최고 공개 수치로 들어와 있다. 저자들은 baseline을 직접 재현하지 않으며, 이 영역의 독립 재현이 반복적으로 평가 설정에 대한 이견으로 이어졌다는 것을 그 이유로 든다. LOCA의 시스템 수준 비교(Table 7) 역시 서로 다른 백본을 쓴다.

Scroll은 채점 대상 산출물 자체가 여러 레코드 위의 압축된 view인 카테고리에서 가장 강한 baseline에 뒤진다. 요약, 선호 준수, 시간 추론이다. ingestion이 무거운 파이프라인은 write 시점에 그 압축된 view를 이미 갖고 있는 반면 Scroll은 질의마다 raw 이벤트에서 재구성해야 한다. multi-session reasoning은 모든 시스템의 최약 카테고리로 남아 있고(9.6–26.1), Scroll의 경우 지나치게 정밀한 필터가 증거 집합을 과소 계수한다. LongMemEval에서 `S`에서 `M`으로 갈 때의 열화도 같은 성질이다. 무관한 세션이 늘면 코드가 지지 세션 하나는 찾아내지만 증거의 일부를 놓친다.

약한 백본에서는 격차가 크게 벌어진다. LOCA 256K에서 최고와 최저가 $64$점 차다. 실패는 프로토콜 준수 문제가 아니라 실행 오류와 집계가 많은 과제에서의 조기 종료다. 저자들은 이를 다단계 질의 계획 능력과 증거 충분성 판단 능력의 문제로 보고, frontier 모델 trace 위의 post-training 여지가 있다고 말한다. 비용도 지연 시간이나 달러가 아니라 토큰 수로만 보고되는데, 둘 다 서빙 구성에 의존하기 때문이다. 별도 언급이 없는 한 각 과제는 한 번만 평가된다.

## 🧷 노트 작성자가 본 빈틈

Table 2가 통제된 비교가 아니라는 것은 저자들이 명시하지만, 초록이 내세우는 "최고 공개 메모리 시스템 대비 5.1점"과 "최고 공개 장기 에이전트 대비 37.4점"이라는 수치는 그 단서 없이 읽히기 쉽다. 특히 37.4점은 백본이 다른 MiniMax M3 + ReAct(49.3)와의 차이여서, 컨텍스트 관리 방식의 기여와 백본의 기여가 분리되지 않는다. 컨텍스트 관리 방식만 놓고 백본을 통제한 비교는 Table 3이고 거기서 Scroll과 CodeAct 에이전트의 차이는 256K에서 86.7 대 85.3, 즉 1.4점이다.

eviction 메커니즘의 효과는 실제로는 얇게 검증됐다. Table 3의 $\Delta$가 CodeAct 에이전트에서 -4.0, Scroll에서 -2.6이고, ablation에서 eviction index 제거는 전체 1.8점만 앗아 간다. 두 메모리 벤치마크는 세션 경계마다 raw 컨텍스트를 비우는 프로토콜로 돌기 때문에 eviction이 실제로 압박받는 조건인지 불분명하다. 즉 논문에서 가장 큰 이득은 손실 없는 Event Log에서 나오고(Figure 3의 Overall 막대에서 읽으면 ingestion 시점에 요약으로 대체한 손실 변형이 0.20, 전체 Scroll이 0.73이며 본문은 손실 변형을 19.9로 적는다), 영속 kernel은 별도의 ablation에서 Scroll w/o REPL이 7.3점 낮은 것으로 보고되고, 논문이 알고리즘으로 제시한 세 번째 기여인 계층화된 eviction index는 측정된 기여가 가장 작다. $\rho$와 $k$의 실제 값, 32K 관찰 상한과 1000행 SQL 상한이 어떻게 정해졌는지도 본문에 없다.

샌드박스는 fail-closed이고 Event Log가 kernel에서 읽기 전용이라고 서술되지만, 모델이 작성한 임의 코드를 실행하는 시스템의 안전성 평가나 실패 사례는 보고되지 않는다. 실행 오류가 약한 백본의 주된 실패 원인으로 언급될 뿐, 오류 빈도나 복구 동작에 대한 수치가 없다. 부록 D의 "성공한 trajectory는 제출 전에 반증 질의를 발행하지만 실패한 것은 결코 발행하지 않는다"는 관찰도 네 개의 예시 trajectory와 저자들의 정성적 분석에 기반한 것이고, 실행 전체에 걸친 집계 수치로 뒷받침되지 않는다.

## 🧵 결론과 다음 단계

Scroll은 컨텍스트 관리를 영속적 Session Environment 위의 명시적 모델 정책으로 만든다. 모델은 `exec`로 외부화된 상태를 검색·계산하고 `print`로 무엇이 다음 컨텍스트로 들어갈지 정하며, 하네스는 결정적 저장·실행·복구를 제공한다. 저자들은 이 정책이 다시 frontier 모델에서 더 작은 모델로 distill될 수 있다고 본다. 성공한 trajectory는 두 가지 결정을 지도한다. *context retrieval*(언제 어떻게 에이전트 히스토리 위의 검색 코드를 쓸 것인가)과 *context injection*(어떤 계산 결과를 working window로 print해 돌려보낼 것인가)이다. 다음 계획은 하부 컨텍스트 메커니즘은 고정한 채 frontier 모델 trace를 supervised fine-tuning 또는 policy distillation에 쓰는 것이다.
